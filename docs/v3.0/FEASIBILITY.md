# V3.0 鸿蒙专用界面：第一轮可行性研究

研究日期：2026-09-23。基线：V2.7.0+6106，应用源码 `90bc58fc3`，版本归档 `f10e29176`。本轮只增加研究文件和只读包检查工具，没有改动应用行为、删除业务功能或调整用户设置。

## 结论

可以彻底替换现有 Material 风格的页面和交互，并逐步消除自有 UI 对 Material 组件的依赖。建议保留业务与播放器能力，建立鸿蒙专用组件层，优先重建首页、播放页、评论和全局导航。不能通过删除 `material_ui`、批量改名或只换主题完成。

“鸿蒙应用”不等于“必须重写所有 Dart 逻辑”；“移除 Material 外观”也不等于“已经消除了 Material 依赖”。Flutter 的 Widgets、渲染、手势层在 Material 组件层之下，可以作为自定义鸿蒙界面的基础。这个分层由 [Flutter 官方架构文档](https://docs.flutter.dev/resources/architectural-overview)说明。

本报告建议的终态：面向用户只提供鸿蒙风格；新 UI 不再以 Material 配色/组件参数作为设计接口；自有 UI 中的旧 Material 实现和兼容 shim 分阶段删除。第三方库的间接依赖另外列账，不能把隐藏 import 当成完成清理。

直接耦合点：

- `lib/harmony_adapt/harmony_theme.dart` 通过 Material 按钮、卡片、输入框主题改变外观，仍属过渡实现。

- `ohos/.../pages/Index.ets` 已经有 HDS 导航与 FlutterPage；原生 LoadingProgress 也已通过 PlatformView 接入，可复用桥接经验。

### 真机可观察交互

本轮查看了官方版单屏 **1008×2232** 画面与控件树，详见 [观察矩阵](INTERACTION_MATRIX.md)。当前确认的是局部场景：

- 单屏沉浸播放的一个横向视频场景，点赞、投币、收藏、评论排在底部，与左侧弹幕入口同属底部区域；合集在进度条上方。这与此前 iOS 参考图的右侧竖排操作不同。
- 评论显示为下方大面板，上方仍有视频区域，评论输入入口固定在面板底部。
- 一次系统 Back 后，评论节点消失，下层播放页节点仍在。不能据此推断嵌套弹层、输入法和折叠时的所有返回行为。

截图期间存在内容切换，可能有用户同时操作；已询问是否可以独占设备，未获答复前暂停进一步点击。没有执行点赞、投币、关注、评论发送等账号写入操作。原始界面截图与元信息仅留本机临时目录，仓库不收录观看内容、账号信息或设备标识。

## 技术路线比较

| 路线 | 能达到的目标 | 代价与风险 | 结论 |
| --- | --- | --- | --- |
| 继续套 Material 主题 | 外观更接近鸿蒙 | 控件逻辑、主题和弹层依赖仍在 | 不满足本轮重构目标 |
| 保留 Flutter/Dart 业务，重建鸿蒙 UI，复用现有 ArkUI 系统组件 | 自有页面可逐步去 Material，保留播放与接口资产 | 需自建输入、导航、弹层、可访问性等基础能力，并清理第三方依赖 | 建议作为 V3.0 首选路线 |
| ArkUI 重建整个 UI，Dart 业务经桥接保留 | UI 使用原生组件 | 双侧生命周期、状态流、列表大数据和播放器纹理桥接显著复杂 | 先做最小原型，再决定扩展 |
| 全部迁移 ArkTS/ArkUI 与原生播放链 | 完整原生技术栈 | 接口、账号、缓存、字幕、弹幕和播放策略需迁移/重写 | 独立重写项目，不能按普通版本更新估算 |

不能因为 Flutter 在 Android/iOS 的 PlatformView 有已知性能权衡，就推断鸿蒙必然同样表现。本项目需要在使用的 OHOS Flutter 分支和 Mate XTS 上实测。尤其避免“每一个列表卡片、按钮都是独立原生 View”的方案：先比较整页/整区域承载与绘制式组件，而不是预设大量桥接一定更快。

## 分阶段实施与验收

1. **固定参考行为**：以官方 8.47.1 为观察样本，补齐首页、普通/沉浸播放、评论、合集、更多菜单、搜索、设置、返回和折叠。记录版本、屏幕形态、操作前提、操作结果和例外；服务端实验或账号设置可能影响行为。
2. **建立鸿蒙组件层**：独立颜色/文字/间距/圆角/材质/动效变量；AppShell、导航、按钮、开关、输入、列表项、Sheet、对话框、Toast、刷新、加载等。不把 ThemeData/ColorScheme 暴露为新公共设计 API。
3. **验证一条完整流程**：首页 → 视频 → 评论/合集 → 返回首页，包含真实流媒体、折叠、后台恢复。比较绘制式 UI 与必要的原生区域承载；连续播放过程中不重复创建播放器。
4. **按页面迁移**：先首页/播放/评论和公共弹层，再设置、搜索、我的、动态及剩余业务页。我的和动态保留用户认可的信息组织，不因迁移而盲目重排。
5. **功能精简**：按用户逐项确认的清单删除或合并，旧设置有迁移映射；移除的是入口、行为还是数据需要分清。见 [决策台账](FEATURE_DECISIONS.md)。
6. **删除旧实现**：迁移完再删除自有 Material 页面、shim、MD3 配色/动效、旧图标依赖；替换或隔离 GetMaterialApp/SmartDialog/旧嵌套滚动所需的 Material 路径。保留原项目许可证和来源说明。
7. **发布门槛**：全量回归通过，三种屏幕形态及旋转/分屏/大字号/深浅色/游客/登录状态完成实际操作；用户数据覆盖升级通过，性能基线不退步。V2.7 已安装但尚待的真实刷新与物理三屏交互验收也应补齐。

## 预估与关键风险

以下是按一个熟悉现有项目的开发者估算的人日区间，不是承诺工期；尚未得到功能删减清单，也未完成全部官方交互采样，置信度低。

- 行为研究、组件定义与完整流程原型：约 8–15 人日。
- 保留业务的 UI 重构、迁移和完整验收：约 60–120 人日，随最终保留页面和第三方替换范围变化。
- 全 ArkUI 且大部分业务跨语言重写：约 150–300+ 人日；需单独立项评估，不能把它作为“去 Material”的必经步骤。

高风险：输入框选择/复制/键盘避让与无障碍；弹层、侧滑和路由返回优先级；折叠时的播放器实例/方向锁/纹理连续性；游客及账号切换；历史、收藏、缓存、弹幕、字幕、空降等原有业务；原生与 Flutter 两侧 Insets、字体和 DPR 的统一。

性能目标在实测 V2.7 基线后冻结：以实际刷新率计算帧预算（60Hz 约 16.7ms，120Hz 约 8.3ms），记录 p95/p99 帧耗时、切视频首帧、内存峰值及长时间播放趋势。暂时没有测量值，不能承诺“完全无卡顿”。
